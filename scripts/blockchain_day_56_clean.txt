Contrast Uniswap v3 (where every liquidity pair is deployed as an independent contract, meaning multi-hop swaps transfer tokens between separate contracts, burning massive gas) with Uniswap v4: 1) The Singleton Architecture (ALL liquidity pools reside in a single smart contract: `PoolManager.sol`, enabling multi-hop swaps to execute with zero intermediate token transfers!); 2) Flash Accounting with Transient Storage (EIP-1153: `TSTORE` and `TLOAD`, clearing state at the end of the transaction for 100 gas per slot!); and 3) The Hooks Architecture: custom plugin contracts that execute logic before/after pool initialization, liquidity changes, and swaps (e.g. Dynamic Fees, On-Chain Limit Orders, TWAMM, and Volatility Oracles). Correct: Option B) Hook Address Flag Bitmask Mismatch: The developer deployed the hook using a standard deployment without mining a specific address! In Uniswap v4, the PoolManager checks: 'if (uint160(hookAddress) & BEFORE_SWAP_FLAG != 0) call beforeSwap()'. Because the deployed address did not have the BEFORE_SWAP bit set to 1, the PoolManager assumed the hook does not implement beforeSwap and skipped it! Hooks must be deployed using CREATE2 salt mining tools (like cast create2) to ensure the address matches its declared permissions. • Debrief: Uniswap v4 uses address-based permission flags to achieve maximum gas efficiency. Each hook callback (beforeInitialize, afterInitialize, beforeSwap, afterSwap...) corresponds to a specific bit in the 160-bit contract address. Developers must use CREATE2 mining to find a salt that generates an address whose leading bits match their hook's required callback flags.
