Day 41 Proxy Pattern Foundations: delegatecall, Storage Collision Hazards & The Implementation Split Stage 3: Advanced Specialization & Scale Month 2 • Block 9 • 4 Quests 🎯 Spoken Goal & Invariant: Goal: Confront the fundamental dilemma of smart contract engineering: Immutability versus Upgradeability. Once deployed to the blockchain, a contract's bytecode is permanently immutable; it cannot be edited or patched. Enter the Proxy Pattern: splitting an application into two distinct contracts: 1) A Proxy Contract (holds all persistent state variables, balances, and funds; contains a fallback function that forwards all incoming calls via `delegatecall` to an implementation address); and 2) An Implementation / Logic Contract (contains the executable business logic, but holds ZERO state). Master the deadliest hazard of proxy patterns: Storage Layout Collisions (if the Implementation declares variables in slots that collide with the Proxy's internal variables, contract memory is corrupted and destroyed!). Invariant: Proxy Storage Decoupling Invariant: The Proxy and Implementation share the EXACT same storage space (the Proxy's storage); the Implementation's state variable declarations must align perfectly with the storage slots established in V1; state variables must NEVER be reordered, deleted, or inserted between existing variables. ⚠️ Failure Mode & tryIt Bug: Failure: Adding a new state variable at the top of an upgraded Implementation contract: 'uint256 public newVar;' declared before existing variables shifts all subsequent variables down by 1 slot; reading 'balances[user]' now reads the wrong slot, corrupting all account balances. tryIt Friction: Construct a minimal Delegatecall Proxy from scratch in Solidity: deploy Proxy with an implementation address stored at custom EIP-1967 storage slot (`bytes32(uint256(keccak256('eip1967.proxy.implementation')) - 1)`); deploy ImplementationV1 with `uint256 public count`; call increment() through the proxy; deploy ImplementationV2 adding a decrement() function; upgrade the proxy; and verify that `count` preserves its value without storage collisions. 🪜 3-Tier Socratic Hint Ladder: [1. Fix: "Standardized EIP-1967 slots protect proxy metadata."] 🧩 Situational Diagnostic Puzzle: "A developer deploys an upgradeable contract behind a proxy. In the Implementation contract, the developer writes: 'constructor() { owner = msg.sender; }'. When interacting with the contract through the Proxy, calling an onlyOwner function reverts with 'Unauthorized', and owner is address(0). Why did the constructor fail to initialize the owner?" Correct: Option B) Constructor vs Initializer Execution Context: Constructors run ONCE during deployment in the context of the IMPLEMENTATION contract's storage! The Proxy's storage was never touched during constructor execution! When users interact through the Proxy, the Proxy's slot 0 (owner) remains 0x0! In upgradeable contracts, constructors must be replaced with an 'initialize()' function marked with OpenZeppelin's 'initializer' modifier, executed via delegatecall through the Proxy. • Debrief: Constructors never run in the context of a proxy. Code inside a constructor modifies only the implementation contract's storage at deployment time. Upgradeable contracts must use regular functions (typically named 'initialize()') guarded by the 'initializer' modifier, called explicitly through the proxy to write initial values to the proxy's storage.
