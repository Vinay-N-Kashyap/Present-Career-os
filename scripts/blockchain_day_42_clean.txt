Day 42 Transparent Upgradeable Proxy (TUP): Admin Fallback Collisions & Function Selector Clashes Stage 3: Advanced Specialization & Scale Month 2 • Block 9 • 4 Quests 🎯 Spoken Goal & Invariant: Goal: Master the most battle-tested upgradeability pattern in Ethereum history: The Transparent Upgradeable Proxy (TUP). Confront the subtle and deadly hazard of Function Selector Clashing: in Solidity, function calls are identified by their first 4 bytes (`bytes4(keccak256(signature))`). An administrative function in the Proxy (e.g. `upgradeTo(address)`) might accidentally have the EXACT SAME 4-byte selector as a user function in the Implementation (e.g. `payout(address)`)! If a user calls `payout()`, the proxy intercepts it as `upgradeTo()`! Deconstruct how TUP solves this: The Transparent Rule (if msg.sender is the Admin, calls are handled by the proxy for administration and NEVER forwarded; if msg.sender is any other user, calls are ALWAYS forwarded via delegatecall). Understand why TUP uses a dedicated `ProxyAdmin` contract. Invariant: Transparent Proxy Disambiguation Invariant: The proxy must strictly bifurcate execution based on caller identity: admin calls are handled locally by the proxy without delegatecall; non-admin calls are transparently forwarded to the implementation; zero function selector ambiguity can exist. ⚠️ Failure Mode & tryIt Bug: Failure: Admin attempting to interact with regular business logic through a Transparent Proxy; because the admin is recognized as Admin, the proxy does NOT forward the call, causing user functions to revert or behave unpredictably. tryIt Friction: Construct a Transparent Upgradeable Proxy with ProxyAdmin in Foundry: generate a 4-byte selector collision between proxy management functions and implementation functions; demonstrate how TUP separates admin vs user contexts; deploy ProxyAdmin; execute an upgrade from V1 to V2 through ProxyAdmin; and verify that regular users interact with business logic cleanly. 🪜 3-Tier Socratic Hint Ladder: [1. Nudge: "Why must the ProxyAdmin contract be the admin of a Transparent Proxy rather than an individual EOA?"] → [2. Memory: "Because if an individual developer's EOA is the admin, that developer can NEVER interact with the contract as a normal user! Any time they try to call transfer() or swap(), the proxy intercepts the call looking for administrative functions! Fix: "ProxyAdmin cleanly separates admin duties from user interactions."] 🧩 Situational Diagnostic Puzzle: "An engineer deploys an Implementation contract for a Transparent Proxy. The contract includes an administrative function 'function setFee(uint256 fee) external onlyOwner'. The protocol admin calls 'proxy.setFee(50)' from their admin wallet. The transaction reverts with 'Transaction reverted: function does not exist'. The admin confirms 'setFee' exists in the implementation. Why did the call revert?" Correct: Option B) Transparent Proxy Admin Interception: Because the caller was the Proxy Admin, the Transparent Proxy checked its OWN contract for a function named 'setFee'! Since 'setFee' is part of the implementation (not the proxy's administrative interface), and the transparent rule prevents admin calls from ever forwarding to the implementation, the call reverted! To call implementation functions, the admin must interact from a non-admin address, while administrative functions like 'upgradeTo' must be called via ProxyAdmin. • Debrief: This is the exact reason Transparent Proxies require a ProxyAdmin contract. Under the transparent proxy rule, calls from the admin address are NEVER forwarded to the implementation. If the admin tries to invoke a standard contract function, the call fails. Routing upgrades through a dedicated ProxyAdmin contract solves this operational hazard.
