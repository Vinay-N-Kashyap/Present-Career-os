Day 43 Universal Upgradeable Proxy Standard (UUPS - EIP-1822): Implementation Upgrades & Self-Destruct Risks Stage 3: Advanced Specialization & Scale Month 2 • Block 9 • 4 Quests 🎯 Spoken Goal & Invariant: Goal: Upgrade to the modern, gas-efficient standard recommended by OpenZeppelin: The Universal Upgradeable Proxy Standard (UUPS - EIP-1822). Contrast UUPS with Transparent Proxies: In TUP, upgrade logic resides inside the Proxy (requiring expensive caller checks on EVERY single transaction, costing ~2,000 extra gas per call). In UUPS, upgrade logic (`upgradeToAndCall`) resides inside the IMPLEMENTATION contract! The proxy becomes a wafer-thin generic delegatecall forwarder. Analyze the benefits: drastically lower deployment gas, cheaper runtime calls, and the ability to eliminate upgradeability in future versions! Confront the existential threat of UUPS: If an upgraded implementation forgets to inherit `UUPSUpgradeable`, the contract can NEVER be upgraded again! Analyze historical selfdestruct vulnerabilities on uninitialized implementations (the Wormhole / OpenZeppelin vulnerability). Invariant: Implementation-Side Upgrade Invariant: In UUPS, the authorization and logic for upgrading reside strictly in the implementation contract; every deployed implementation MUST inherit UUPSUpgradeable and authorize upgrade permissions, or the proxy becomes permanently non-upgradeable. ⚠️ Failure Mode & tryIt Bug: Failure: Deploying an uninitialized UUPS implementation contract on-chain without calling '_disableInitializers()'; an attacker calls 'initialize()' directly on the implementation contract, becomes owner, and executes 'selfdestruct', destroying the implementation bytecode and bricking all associated proxies permanently. tryIt Friction: Implement an audited UUPS Upgradeable Protocol in Foundry: deploy UUPS Proxy pointing to ImplementationV1 with `_disableInitializers()` in constructor; initialize state through the proxy; deploy ImplementationV2 adding new features and inheriting UUPSUpgradeable; execute upgrade through the proxy; and write a Foundry test proving that forgetting UUPSUpgradeable in V2 breaks future upgrades. 🪜 3-Tier Socratic Hint Ladder: [1. Nudge: "Why must UUPS implementation contracts include '_disableInitializers()' in their constructors?"] → [2. Memory: "Because an implementation contract sits deployed on the blockchain as an independent contract! If its constructor does not lock initialization, anyone can call 'initialize()' directly on the logic contract, seize ownership of it, and if it has a selfdestruct opcode, destroy the contract and brick all proxies!"] → [3. Fix: "Always call _disableInitializers() in the logic constructor."] 🧩 Situational Diagnostic Puzzle: "A development team upgrades their UUPS protocol to V2. The upgrade succeeds! However, next month, when attempting to deploy V3, calling 'upgradeTo(V3)' reverts with 'Function does not exist'. The team discovers that ImplementationV2 forgot to inherit 'UUPSUpgradeable'. Can the team recover the upgradeability of their proxy?" Correct: Option B) Permanent Upgradeability Forfeiture (Bricked Upgrade Logic): No! In UUPS, the proxy has ZERO upgrade logic of its own—it strictly forwards calls to the implementation! Since ImplementationV2 lacks 'upgradeTo()', there is physically no code in the system capable of changing the implementation address at EIP-1967 slot! The proxy is permanently locked to ImplementationV2 forever. It has effectively become an immutable contract. • Debrief: This is the primary operational risk of UUPS. In Transparent Proxies, upgrade logic lives in the proxy and can never be lost. In UUPS, upgrade logic lives in the implementation. If an implementation upgrade omits the upgrade function, the proxy permanently loses the ability to upgrade. OpenZeppelin's Upgrades Plugins catch this at deployment time.
