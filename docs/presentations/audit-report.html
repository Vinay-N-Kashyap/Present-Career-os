CAVCAV-01
Role verification used user JWT — RLS could allow self-written role escalation
Dual fix: service-role queries + database-level privilege-escalation trigger
✓ CLOSED
Fix A — getAuthoritativeSupabaseClient (lib/server/requireAuth.ts:72–86)
function getAuthoritativeSupabaseClient(userToken: string) { const serviceKey = process.env.SUPABASE_SERVICE_ROLE_KEY || ''; if (serviceKey) { // Service-role: bypasses RLS entirely — true DB state, untamperable return createClient(url, serviceKey, { auth: { persistSession: false } }); } // Fallback (dev env without service key): anon + user JWT return createClient(url, anon, { global: { headers: { Authorization: `Bearer ${userToken}` } }, auth: { persistSession: false }, }); } // Used by requireFacultyOrAdminUserFromRequest AND requireAdminUserFromRequest
Fix B — Database trigger (supabase/schema.sql:268–296)
create or replace function public.prevent_privilege_escalation() returns trigger language plpgsql security definer as $$ begin if new.role is distinct from old.role or new.pins is distinct from old.pins or coalesce(new.subscription_tier,'free') is distinct from coalesce(old.subscription_tier,'free') or new.ats_score is distinct from old.ats_score or new.trust_score is distinct from old.trust_score then if auth.uid() is not null and auth.uid() = old.id then -- Self-service update: silently force old values back new.role := old.role; new.pins := old.pins; new.subscription_tier := old.subscription_tier; new.ats_score := old.ats_score; new.trust_score := old.trust_score; end if; end if; return new; end;$$; create trigger trg_prevent_privilege_escalation before update on public.users for each row execute function public.prevent_privilege_escalation();
Defence-in-depth: In production (service key set), role queries bypass RLS and read the authoritative row — a tampered role value is never returned. In dev (service key absent), the anon+JWT path applies, but the DB trigger intercepts any self-UPDATE that would change role, pins, ats_score, or trust_score and silently restores old values. Both defences must be defeated simultaneously for privilege escalation — which is not possible without direct Supabase superuser access. ✓
CAVCAV-02
PATCH /api/auth/profile accepted verified:true from any authenticated session
Server-side sanitisation strips verified flag from all portfolio items for non-privileged callers
✓ CLOSED
Evidence — sanitizePortfolioItems + stripSelfServicePrivileges (lib/supabaseService.ts:273–316)
function sanitizePortfolioItems(items: any[]): any[] { if (!Array.isArray(items)) return []; return items.map(item => { if (typeof item !== 'object' || !item) return item; return { ...item, verified: false }; // ← forced off unconditionally }); } function stripSelfServicePrivileges(row: Record<string, any>, allowPrivileged = false) { if (allowPrivileged) return row; // privileged callers (verify-endorsement) bypass delete row.role; delete row.subscription_tier; delete row.pins; // ... // CAV-02 FIX: strip verified:true from every portfolio array const ob = { ...row.onboarding_answers }; for (const key of [ 'portfolio_projects', 'portfolio_timeline', 'portfolio_recommendations', 'portfolio_achievements', 'portfolio_certificates' ]) { if (Array.isArray(ob[key])) { ob[key] = sanitizePortfolioItems(ob[key]); } } row.onboarding_answers = ob; return row; }
How it closes the gap: Every self-service PATCH call goes through stripSelfServicePrivileges(row, false) before writing to Supabase. Any verified: true submitted by the client is overwritten to false server-side, regardless of what the client sent. The only code path that can write verified: true is /api/portfolio/verify-endorsement (which calls with allowPrivileged: true after a faculty role check). curl/Postman bypass is no longer possible. ✓

Role Verification — 3 Layers
L2 — Service-role DB read
getAuthoritativeSupabaseClient uses the service key (bypasses RLS) to read the true role from the users table when the key is available.
Role Verification — 3 Layers
L3 — DB trigger
trg_prevent_privilege_escalation intercepts any self-service UPDATE that changes role, pins, ats_score, or trust_score and silently reverts it. Runs even against direct Supabase REST API calls.

Portfolio Verification — 2 Layers
L2 — PATCH handler sanitisation
stripSelfServicePrivileges forces verified: false on all portfolio items for any self-service PATCH, regardless of what the client submitted.
